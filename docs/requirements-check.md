# Проверка выполнения лабораторной № 2, вариант 2

Проверены [общее условие](../README.md), [вариант 2](../v2/README.md),
[OpenAPI](../v2/%5Binst%5D%5Bv2%5D%20Hotels%20Booking%20System.yml) и исходная
[коллекция Postman](../v2/postman/collection.json). Дата проверки: 17 октября 2026.

**Все бизнес-сценарии варианта реализованы.** По инфраструктуре подготовлены
Docker и GitHub Actions, однако их фактическое выполнение в этой проверке
не подтверждено. Поэтому формальная приемка задания еще не завершена.

## Общие требования

| Требование README | Результат и подтверждение |
|---|---|

| Сборка и unit-тесты в Classroom | `.github/workflows/classroom.yml` вызывает `make check`, собирает образы и запускает приемочную коллекцию. Дополнительный workflow проверяет SQL и E2E. Сам GitHub Actions в рамках проверки не запускался. |
| В конфигурации выбран вариант 2 | Classroom и `.github/classroom/autograding.json` используют `v2/postman`. В рабочих файлах конфигурации нет `<variant>`. |
| Код размещен в GitHub, приемка Classroom успешна | `origin` настроен, но текущие изменения локальные, многие файлы еще не добавлены в Git. Публикация и зеленый результат Classroom не подтверждены. |

## Публичные операции

| Операция | Что проверено |
|---|---|
| `GET /api/v1/hotels` | Отели из БД, пагинация, поля отеля и цена. По умолчанию page=1, size=10. |
| `GET /api/v1/me` | Объединение бронирований, оплат и лояльности для указанного пользователя. |
| `GET /api/v1/reservations` | Только бронирования пользователя, включая отмененные; пустой результат — `[]`. |
| `GET /api/v1/reservations/{uid}` | Бронь с данными отеля и оплаты; чужая или отсутствующая бронь — `404`. |
| `POST /api/v1/reservations` | Проверка отеля, даты и стоимости, скидка до увеличения счетчика, оплата и сохранение брони. Успех — `200`, ошибки валидации — `400`. |
| `DELETE /api/v1/reservations/{uid}` | Отмена брони и оплаты, уменьшение счетчика и пересчет уровня. Успех — `204`; чужая или отсутствующая бронь — `404`. Повтор не уменьшает счетчик повторно. |
| `GET /api/v1/loyalty` | Статус, скидка и счетчик; новый пользователь получает BRONZE/5%/0. |

Контроллеры и DTO находятся в `internal/gateway/adapters/http`; прикладные
методы — в `internal/gateway/application`. Все семь операций проверяются
HTTP-тестами; исходная коллекция Postman содержит восемь запросов, включая
повторное чтение лояльности после создания бронирования.

## Предметные правила

- Ночи считаются как разница календарных дат. Цена умножается на число ночей,
  затем применяется скидка. Нет проверки конечного количества мест в отеле:
  по условию их бесконечно много.
- BRONZE: счетчик 0–9, скидка 5%; SILVER: 10–19, скидка 7%; GOLD: от 20,
  скидка 10%. Проверены повышение и понижение на обеих границах.
- Скидка текущей брони определяется до увеличения счетчика. Десятая бронь нового
  пользователя получает 5%; следующая — 7%.
- Отмена меняет оба статуса на `CANCELED`. Счетчик не становится отрицательным,
  повторная отмена не меняет его повторно.
- Пользователь проверяется перед чтением оплаты и изменением чужой брони;
  Reservation учитывает владельца в SQL.
- В миграциях есть исходный отель Ararat Park Hyatt Moscow с указанным UUID
  и ценой 10000, а также Test Max со счетчиком 25, GOLD и скидкой 10%.
- Миграции выполняются отдельной CLI Goose. Проверены применение, откат
  и повторное применение на временных тестовых базах.
- Домены зависят только от стандартной библиотеки. Контроллеры используют
  интерфейсы сценариев, прикладные сервисы — порты репозиториев/клиентов.
  Конкретные зависимости собираются вручную в `cmd/`.

## Неоднозначности и принятые решения

1. **Тип скидки в ответе создания.** В OpenAPI свойство
   `CreateReservationResponse.discount` объявлено как `string`, но пример содержит
   число `10`. Postman сравнивает его с числовой скидкой из Loyalty без
   преобразования типа. Реализация возвращает **число**. Таким образом, буквального
   соответствия этому одному свойству схемы нет; выбран пример и приемочная
   коллекция. Исходное условие и тесты не изменялись.
2. **SQL из условия.** Деньги хранятся как `BIGINT` вместо `INT`, даты проживания
   как `DATE` вместо `TIMESTAMP WITH TIME ZONE`; `end_data` названо `end_date`.
   Добавлены ограничения, индексы и журналы идемпотентности. Перечислены также
   в [описании сервисов](services.md).
3. **Нумерация страниц.** OpenAPI допускает page=0, пример использует page=1.
   Оба значения означают первую страницу; дальше нумерация с единицы.
4. **Округление денег.** Условие не задает его для дробной суммы скидки.
   Округляется конечная сумма до целого рубля, половины вверх. Все вычисления
   целочисленные, проверяются на переполнение.
5. **Дата проживания.** Используется `YYYY-MM-DD`, как в примерах и Postman.
   Прошедшие даты разрешены: приемочная коллекция использует 2021 год.
6. **Дополнительные enum-значения.** OpenAPI допускает RESERVED и REVERSED,
   однако описание сценариев и SQL требуют PAID/CANCELED. Отдельных операций
   резервирования без оплаты или возврата с REVERSED в задании нет.

В Classroom добавлена явная установка Newman v6.2.1 в окружение runner:
команда из `autograding.json` вызывает `newman` напрямую. Установка внутри
стороннего action не гарантировала бы доступность CLI следующему шагу.
Оба workflow используют команды нового [Makefile](../Makefile).

Проверка с настоящим PostgreSQL выполняется нативно через `make test-system`:
свой временный кластер, миграции, SQL/race-тесты, четыре процесса, Postman,
дополнительные системные сценарии и проверки healthcheck. Версия локальной БД —
PostgreSQL 18.6, в Compose закреплен PostgreSQL 13. Нативный прогон не подтверждает
работоспособность Docker-образов или совместимость именно с PostgreSQL 13.

Чтобы закончить формальную приемку, нужно выполнить `make up`, `make test-api`
и `make test-e2e` при доступном Docker, затем опубликовать изменения и получить
успешный запуск GitHub Actions/Classroom. Шаг записи оценки в Classroom также
зависит от настроенных секретов преподавательского workflow.

Сохраняемый координатор компенсаций после падения Gateway не реализован:
это ограничение надежности текущего решения, отдельного требования к нему
в лабораторной нет. При сетевых сбоях Gateway пытается выполнить ограниченные
по времени компенсации через идемпотентные команды; их успех зависит от
доступности сервисов. Общей транзакции между сервисами нет.
