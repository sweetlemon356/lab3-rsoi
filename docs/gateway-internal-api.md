# Внутренние контракты, необходимые Gateway

Это реализованные HTTP-контракты Reservation, Payment и Loyalty, которыми
пользуется Gateway. Публичный API Gateway остается заданным в OpenAPI варианта
`v2/`. Устройство и запуск основных сервисов описаны в [services.md](services.md).

## Общие правила

- Префикс: `/internal/v1`. Тела и ответы — JSON с camelCase-полями.
- Даты: календарные `YYYY-MM-DD`, без часового пояса. Прошедшие даты разрешены.
- UUID создаются Gateway до изменяющих запросов и передаются в URL. Внутренние
  PUT-запросы с тем же UUID идемпотентны; другой payload того же ресурса отклоняется.
- Суммы — целые рубли (`int64` в Go, совместимые с SQL задания). Расчет выполняет
  Reservation, скидка берется до учета нового бронирования. Дробные рубли после
  скидки округляются до ближайшего целого, половины вверх. Gateway ничего
  не пересчитывает; передает итоговую сумму в Payment.
- Чтение: `200` и JSON. Создание PUT: `200` или `201`. Изменения без результата:
  `200` или `204`. Ошибки не возвращаются под видом успешного пустого ответа.
- GET отелей публично использует page=1 и size=10 по умолчанию. Для совместимости
  с minimum=0 в OpenAPI page=0 также означает первую страницу; остальные страницы
  нумеруются с 1. Допустимые size: 1..100. Метаданные отражают переданные параметры.
- `404` при получении чужой/отсутствующей брони или расчете неизвестного отеля
  означает отсутствие публичного ресурса. Отсутствие оплаты, на которую ссылается
  существующая бронь, — ошибка зависимого сервиса, а не публичный `404`.

## Reservation Service

| Метод | Путь | Вход | Выход |
|---|---|---|---|
| GET | `/internal/v1/hotels?page=1&size=10` | Пагинация | Страница отелей, как в публичном контракте |
| GET | `/internal/v1/reservations` | `X-User-Name` | Массив ReservationData |
| GET | `/internal/v1/reservations/{uid}` | `X-User-Name` | ReservationData или 404 |
| POST | `/internal/v1/reservations/quote` | QuoteRequest | ReservationQuote |
| PUT | `/internal/v1/reservations/{uid}` | SaveReservationCommand | 200/201 |
| PUT | `/internal/v1/reservations/{uid}/cancellation` | `{"username":"Test Max"}` | 200/204 |

`ReservationData`:

```json
{
  "reservationUid": "9b4ba1f7-e5ac-465b-ace4-7b54dec20f9a",
  "username": "Test Max",
  "paymentUid": "5c9ced89-f43a-4ac4-a516-e6660e5bddcb",
  "hotel": {
    "hotelUid": "049161bb-badd-4fa8-9d90-87c9a82b0668",
    "name": "Ararat Park Hyatt Moscow",
    "fullAddress": "Россия, Москва, Неглинная ул., 4",
    "stars": 5
  },
  "startDate": "2021-10-08",
  "endDate": "2021-10-11",
  "status": "PAID"
}
```

В QuoteRequest: `hotelUid`, `startDate`, `endDate`, `discount` (целый процент).
Reservation проверяет отель, период и скидку, считает ночи и итоговую стоимость.
ReservationQuote возвращает `hotelUid`, `startDate`, `endDate`, `price`.

В SaveReservationCommand: `username`, `paymentUid`, `hotelUid`, `startDate`,
`endDate`. Статус создаваемой брони — PAID. UID брони уже находится в URL.

Reservation обязан ограничивать чтение владельцем. Gateway дополнительно
проверяет `username` в полученных данных перед чтением оплаты и изменениями.

## Payment Service

| Метод | Путь | Вход | Выход |
|---|---|---|---|
| GET | `/internal/v1/payments/{uid}` | — | `{"status":"PAID","price":27000}` |
| PUT | `/internal/v1/payments/{uid}` | `{"price":27000}` | 200/201 и состояние оплаты |
| PUT | `/internal/v1/payments/{uid}/cancellation` | — | 200/204 |

Создание гарантирует PAID и принятую сумму; повтор отмены безопасен.

## Loyalty Service

| Метод | Путь | Вход | Выход |
|---|---|---|---|
| GET | `/internal/v1/loyalty/{username}` | Имя как один URL-encoded сегмент | status, discount, reservationCount |
| PUT | `/internal/v1/loyalty/{username}/reservations/{uid}` | — | 200/204, учесть бронь |
| DELETE | `/internal/v1/loyalty/{username}/reservations/{uid}` | — | 200/204, отменить учет брони |

Неизвестный пользователь получает BRONZE / 5% / 0. Повторный PUT одной брони
не увеличивает счетчик повторно; повторный DELETE не уменьшает его повторно.
Границы: 0..9 BRONZE, 10..19 SILVER, 20+ GOLD. Loyalty атомарно обновляет учет,
счетчик, статус и скидку в своей БД.

## Частичные сбои

Создание: получить скидку, получить расчет, создать оплату, сохранить бронь,
учесть бронь в Loyalty. При ошибке любого изменяющего запроса Gateway пытается
отменить и сам запрос с неопределенным результатом, и предыдущие изменения
в обратном порядке. Для этого UUID известны до отправки запросов.

Отмена: проверить владельца, отменить оплату, отменить учет в Loyalty, пометить
бронь CANCELED. При недоступности Loyalty снятие учета помещается в очередь,
после чего отменяется бронь и клиент получает `204`. Если очередь заполнена,
Gateway возвращает ошибку. При других сбоях повторный публичный DELETE продолжает тот же процесс.
Даже если статус брони уже CANCELED, повторяются идемпотентные команды отмены.

**Гарантии реализованных сервисов:** отмена должна фиксировать терминальное
состояние даже для еще не пришедшего создания/учета. Поздний запрос создания
не должен оживлять отмененный UUID. Одного ответа 404 на отмену отсутствующего
объекта недостаточно. Реализацию учета операций выбирает соответствующий сервис.

Gateway использует общий deadline запроса и ограниченный отдельный контекст
для компенсации после отмены исходного контекста. Все компенсации предпринимаются,
даже если одна завершилась ошибкой; ошибки сохраняются и журналируются.
Неудавшиеся компенсации передаются очереди RabbitMQ. Повтор
происходит через 10 секунд с тем же UUID и ограниченным временем попытки.
Задание удаляется только при успехе. Сохраняемого журнала операций и общей
транзакции нет. Поставленные задачи переживают падение Gateway; неподтвержденные сообщения
брокер повторно доставит consumer. Подтверждение отправляется после
успеха, поэтому возможна повторная доставка с тем же UUID.

## Решения по публичным неоднозначностям

Создание возвращает 200, отмена — 204. `discount` возвращается числом, как
в примере и Postman (в одном свойстве OpenAPI ошибочно указан string).
Проверка JSON/параметров дает 400, отсутствие/чужая бронь — 404, ошибка зависимости
— 500 для Reservation/Payment и 503 для Loyalty. Некритичные Payment/Loyalty
при чтении агрегатов дают пустой объект и 200. Превышение общего срока без
ошибки зависимости — 504, отмененный запрос — 408, внутренняя ошибка — 500.
Статус 503 для Loyalty выбран по исходной приемочной коллекции, несмотря на
пример с 500 в README варианта 2.
Внешнему клиенту не передаются адреса сервисов и диагностические тексты зависимостей.
